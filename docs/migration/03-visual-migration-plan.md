## 1 · Screenshot harness

The spec's phone frame is **390 × 844** — identical to Playwright's `devices['iPhone 13']`,
already set as the default in `playwright.config.ts`. Captures compare 1:1 against the
frames with no scaling.

### Layout

```
docs/migration/screenshots/
  baseline/     captured ONCE before Stage 0    <slug>.png
  current/      recaptured after every page     <slug>.png
  diff/         generated by the compare step   <slug>.png
  MANIFEST.md   slug → route → frame → state
```

### What gets built (Stage 0, first commit)

| File                            | Purpose                                                                                      |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| `scripts/screenshots.ts`        | Playwright driver: logs in per role, walks the route table, opens sheets/states, writes PNGs |
| `scripts/screenshot-routes.ts`  | The route table — slug, path, role, pre-actions, target frame                                |
| `scripts/screenshot-compare.ts` | Pixel diff `baseline/` vs `current/`, writes `diff/` + a summary                             |
| `package.json` scripts          | `shots:baseline` · `shots:current` · `shots:compare`                                         |

### Prerequisites (your machine — nothing is installed yet)

```bash
# 1. Dependencies (node_modules is absent)
pnpm install

# 2. Start Docker Desktop, then the services
docker compose up -d          # postgres · redis · minio

# 3. Env — copy and fill (I am blocked from reading .env)
cp .env.example .env

# 4. Database

# 5. Browser for screenshots

# 6. Dev stack with the mock OTP (code 123456)

```

Then: `pnpm shots:baseline` — captures all 58 shots into `baseline/`.

**Nothing in Stage 0 proper begins until `baseline/` exists.** That is the entire
point: it is the only defence against "Patients disappeared, three hours later".

### Toolchain (discovered during Stage 0a)

The repo pins **Node 20 + pnpm 10.33.0**; the machine had **Node 24 + Homebrew pnpm
11.20**, and pnpm 11 requires Node ≥ 22.13 — mutually exclusive. Resolved _without_
touching the repo's `engines`, by honouring its own `packageManager` field:

```bash
fnm install 20 && fnm use 20
corepack enable pnpm && corepack prepare pnpm@10.33.0 --activate
```

`.npmrc` sets `engine-strict=true`, so this is enforced, not advisory. Anyone running
the harness needs the same two lines.

The web suite is the one this migration actually moves, and it is green. **The API
suite is unverifiable until `.env` exists** — so governance §3's "0 failing tests"
means _0 in every suite that can run_, and the API suite must be re-baselined by you
once the stack is up. Flagged rather than assumed.

### Comparison protocol (after every page)

1. `pnpm shots:current` — recapture only the slugs for the page just migrated
2. `pnpm shots:compare` — pixel diff vs baseline
3. **Read the diff.** A large diff is expected (that's the migration). What you're
   hunting is _structural loss_: a missing button, a vanished row, a collapsed section
4. Check the page against its frame side by side
5. `pnpm verify` (lint · typecheck · test)
6. Walk the §5 per-page checklist
7. Commit

### 4.2 — Follow-ups: you were right to push back (your Q7)

I checked all four candidates for extension. None fit — but the answer is still
**not** the full model I originally proposed.

| Candidate                     | Why it can't hold a follow-up                                                                                                                                                                                                                                                                                          |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AppointmentReminder`         | `appointmentId` is a **required FK**. A follow-up exists precisely _before_ an appointment — booking one is the outcome (frame 66's "Book" action). Making the FK nullable would break its `@@index([appointmentId])` and its cascade delete, and the reminder sweep worker iterates it assuming an appointment exists |
| `BillReminder`                | `billId` required; money-scoped                                                                                                                                                                                                                                                                                        |
| `TreatmentPlan` / `Procedure` | A follow-up is not planned work — it's a post-completion obligation. Two of the three rules (extraction → sutures, denture → 2-week check) fire _after_ a procedure completes                                                                                                                                          |
| `Sitting`                     | `@@unique([procedureId, sittingNumber])` and `notesEnc` model delivered clinical work. Inserting "pending review call" rows would corrupt `Procedure.completedSittings` and the frame-38/39 journey rails                                                                                                              |

**But the list itself needs no model at all.** It derives from data that already exists:

- `Prescription.reviewAfterDays` (**this column is already there and unused by any UI**)
- `Procedure.status = COMPLETED` + `completedAt` + a rule table (RCT → day 7, extraction → sutures, denture → 14 days)
- `LabCase` fitted → fit-check

Deriving gives you the whole list, sorted, with overdue computed. What derivation
_cannot_ express is the **resolution**: frame 66's ✓ chip marks a follow-up handled
_without_ booking anything, plus call logging and the 6s undo.

**Revised proposal — one small table, not a full model:**

```prisma
model FollowUpResolution {
  id         String   @id @default(cuid())
  clinicId   String
  patientId  String
  sourceType String   // 'PRESCRIPTION' | 'PROCEDURE' | 'LAB_CASE'
  sourceId   String
  status     String   // 'DONE' | 'SNOOZED'
  resolvedAt DateTime @default(now())
  resolvedById String
  note       String?  // call outcome

  @@unique([clinicId, sourceType, sourceId])
  @@index([clinicId, resolvedAt])
}
```

Endpoints: `GET /follow-ups` (derives, left-joins resolutions, filters out DONE) and
`POST /follow-ups/resolve`.

Why this is better than the model I first proposed:

- **No generation job, no cron, no backfill** — which removes risk #10 from the register
  entirely (a `FollowUp` table would have needed a decision about firing on years of
  historical procedures)
- The rules live in code, so tuning a rule doesn't need a data migration
- 8 columns instead of ~15, and it can be dropped without losing clinical data

Cost: the derive query joins three sources per request. At clinic scale (hundreds of
procedures) that's trivial, and it's cacheable.
